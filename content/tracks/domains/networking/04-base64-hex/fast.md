# Fast path: what's different in C++

- **`constexpr` tables.** The 256-entry decode table is computed by a `constexpr` function and stored in read-only data: no start-up cost, no data race, no static-initialisation-order problem. In C you write the table by hand or generate it; in C++ a `constexpr` loop produces it, and `static_assert` can spot-check it at build time.
- **`unsigned char` as an index.** `char` may be signed; `table[c]` with a negative `c` reads *before* the array. Always `static_cast<unsigned char>(c)` before indexing a 256-entry table.
- **Output buffers as `std::span`.** `std::span<char>` carries the capacity, so `encode_to` can refuse a small buffer instead of overflowing it. The C versions (`b64_encode(const uint8_t*, size_t, char* out)`) trust the caller to have sized `out`, which is the source of many CVEs in real base64 libraries. OpenSSL's `EVP_EncodeBlock`, for instance, returns no error at all and relies on the caller computing `4 * ((n + 2) / 3) + 1`.
- **SIMD.** Production decoders (the `base64` crate, Lemire/Muła's `simdutf` and `fastbase64`) process 16 to 64 characters per instruction with AVX2/AVX-512/NEON and run at memory speed (several GB/s); a table-driven loop like this one does about 1 GB/s. The strict rules are the same for both, which is why the scalar version is the reference.
- **Standard library status.** C++ has no standard base64 or hex codec (C++26 adds `std::to_chars`/`from_chars` for integers only). Boost has `boost::beast::detail::base64` and `boost::algorithm::hex/unhex`; Abseil has `absl::Base64Escape`/`Base64Unescape` and `absl::BytesToHexString`; Python's `base64`/`binascii`, Java's `java.util.Base64`, Go's `encoding/base64` ship with the language.
- **JWT and friends.** JSON Web Tokens use *unpadded URL-safe* base64 for each of their three parts; decoders that tolerate padding or both alphabets have caused signature-verification bypasses.
