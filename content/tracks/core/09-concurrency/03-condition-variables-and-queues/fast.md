# Fast path: what's different in C++

- **`std::condition_variable`** (`<condition_variable>`) works with a `std::unique_lock<std::mutex>`: `wait(lock, pred)` = unlock + sleep + relock + re-check in a loop; `wait_for`/`wait_until` add a timeout; `notify_one`/`notify_all`. **Always use the predicate form.** Spurious wake-ups are allowed by the standard; notifications are not queued (a notify with no waiter is lost), so the state change must be made under the mutex and the predicate checked before sleeping.
- **Shape of a blocking queue**: `mutex` + `deque` + `closed` flag + two condition variables (`not_full`, `not_empty`); `push`: wait for room or closed → add → notify not_empty; `pop`: wait for item or closed → take → notify not_full; `close`: set the flag under the mutex, `notify_all` on both. Return `std::optional<T>`/`bool` to say "closed and empty".
- **Prefer `notify_all` for state changes every waiter cares about** (close, shutdown, flag changes); `notify_one` for "one more unit of work". Notifying after unlocking is fine and avoids a wake-up-then-block.
- **Never busy-wait**, and avoid polling with `sleep_for` when something can notify you. CPU time is the cost; latency is the other.
- **C++20 helpers**: `std::latch` (one-shot countdown), `std::barrier` (reusable phase barrier), `std::counting_semaphore`/`std::binary_semaphore`, `std::atomic<T>::wait/notify_one/notify_all` (waiting on an atomic's value without a mutex), `std::stop_token` + `condition_variable_any` for cancellable waits.
- **Queues in practice**: bounded for backpressure; `close()` (or a poison pill value) for shutdown; `try_push`/`try_pop` and timed variants; multi-producer multi-consumer; lock-free queues exist (Boost.Lockfree, `moodycamel::ConcurrentQueue`) but a mutex + condition variable is the right default. Move-only payloads (`unique_ptr<Task>`) need `std::move` in and out.
