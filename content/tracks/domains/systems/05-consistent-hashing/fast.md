# Fast path: what's different in C++

- **Sorted `std::vector` + `std::lower_bound` is the C++ idiom for "ordered map that is read far more than written".** Java's `TreeMap.ceilingEntry` and Python's `bisect` over a list are the same idea; the standard C++ library also has `std::map::lower_bound`, but a tree of nodes costs a cache miss per level while a vector's binary search touches contiguous memory. For a ring of 100000 points the difference is around 3 to 5 times.
- **`std::inplace_merge`, `std::remove_if` and friends are the algorithms that make the vector approach pleasant.** They are stable, work on iterators, and know nothing about the container, so a sorted `std::vector`, a `std::deque` or a plain array all work. Remember the erase-remove idiom: `remove_if` only *moves* the survivors forward and returns the new end; `erase` actually shrinks the container (C++20 adds `std::erase_if` for that one-liner).
- **Pointers to `unordered_map` keys are stable.** The standard guarantees that rehashing does not move the elements, only the buckets, which is why `Point` can hold `const std::string*` safely. The same is *not* true of `std::vector` or of open-addressing maps such as `absl::flat_hash_map`.
- **Why a 64-bit finalizer on top of FNV?** `std::hash<std::string>` is not specified: it can differ between standard libraries and even between runs, so two servers would disagree about key ownership. A consistent-hash ring needs a hash that is the same everywhere, forever; production systems use MurmurHash3, xxHash or SipHash for this reason.
- **Beyond the ring.** Google's *Maglev* hashing and *jump consistent hash* (a 5-line function with no memory at all) solve the same problem with different trade-offs: perfect balance and speed versus support for removing arbitrary nodes. Rendezvous (HRW) hashing needs no ring and gives the same minimal disruption at the cost of O(N) per lookup.
