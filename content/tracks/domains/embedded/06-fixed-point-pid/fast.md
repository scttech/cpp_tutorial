# Fast path: what's different in C++

- **`int64_t` intermediates are the whole trick, and signed overflow is undefined behaviour.** In C++ (and C) `int * int` that overflows is not "wrapping": the compiler may assume it never happens and optimize on that assumption. So fixed-point code widens first (`static_cast<std::int64_t>(a) * b`) and checks the range explicitly. Java wraps silently; Rust panics in debug and wraps in release unless you ask for `saturating_mul`/`checked_mul`. C++26 adds `std::add_sat`, `std::sub_sat`, `std::mul_sat`, `std::div_sat` in `<numeric>` for exactly this exercise.
- **Operator overloading makes control code readable.** `p = kp * error; integral = clamp(integral + ki * error * dt, lo, hi);` reads like the textbook, while each operator is a saturating, rounding, `constexpr` function that inlines to a handful of instructions. In C the same code is `fx_add(fx_mul(...))`.
- **`constexpr` all the way.** The gains (`Fixed::from_ratio(5, 2)`) are computed by the compiler; no float constant ends up in the binary, which also keeps soft-float routines out of the linked image.
- **Determinism.** Floating point results can differ between compilers, optimization levels and FPU modes (fused multiply-add, x87 extended precision). Integer arithmetic is identical everywhere, so a recorded sensor trace replays to the same actuator trace on a laptop and on the target, which is why safety-critical control code often prefers fixed point even on chips that have an FPU.
- **Libraries.** `boost::fixed_point` (proposed), the C++ Embedded Technical Report's `<stdfix.h>` types (`_Accum`, `_Fract`, saturating or not), `libfixmath`, and CMSIS-DSP (`q15_t`, `q31_t`) all provide this arithmetic; knowing how to write the core operations yourself is how you review them.
