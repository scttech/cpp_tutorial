# Fast path: what's different in C++

- **`std::atomic` and the memory model.** C++11 defines exactly when a write on one thread is visible to a read on another: through *synchronizes-with* edges, created by `release` stores paired with `acquire` loads. This is not an implementation detail of x86; on ARM and POWER the same code needs real barrier instructions, and the compiler may also reorder your plain loads and stores. Java has `volatile` and `AtomicXxx`, Go has channels and `sync/atomic`; C++ gives you the individual orderings (`relaxed`, `acquire`, `release`, `acq_rel`, `seq_cst`) so that the SPSC case can use the cheapest sufficient one.
- **`memory_order_seq_cst` is the default** (the safest and slowest). A good lock-free structure *names* the weaker orders it needs and can say why each is enough. ThreadSanitizer understands them, which is how the tests catch a missing `release`.
- **Cache lines are the real unit of sharing.** `alignas(64)` (or `std::hardware_destructive_interference_size` in `<new>`, C++17) separates variables written by different threads. The cost of false sharing is one of the larger surprises in multithreaded performance.
- **Lock-free is not wait-free is not fast.** Lock-free: some thread always makes progress. Wait-free: *every* operation finishes in a bounded number of steps (this queue). Neither says anything about speed; they promise the *absence of blocking* and therefore of priority inversion and convoying, which is what matters for tail latency.
- **Why SPSC and not MPMC?** One writer per variable removes all the hard problems (CAS loops, the ABA problem, memory reclamation). Disruptor (LMAX), Linux `kfifo`, DPDK rings and Folly's `ProducerConsumerQueue` are SPSC rings like this one.
- **Hardware interference size, `std::atomic<T>::is_always_lock_free`, `std::atomic_ref`** are the C++17/20 tools around this topic.
