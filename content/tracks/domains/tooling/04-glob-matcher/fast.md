# Fast path: what's different in C++

- **Library options.** There is **no glob matching in the C++ standard library** (`<regex>` is a different, slow, backtracking-in-practice engine; `std::filesystem` iterates directories but does not match patterns). POSIX has `fnmatch(3)` and `glob(3)` (C, locale-dependent, no `**`, no braces without `FNM_EXTMATCH`/`GLOB_BRACE`); Boost has `boost::filesystem::glob`-like helpers in `boost::regex` form and **Boost.Wave**; **Abseil**, **gitignore.hpp** and **cpp-glob** implement gitignore-style rules; **RE2** (Google) is the linear-time regex engine whose design this lesson follows. Rust's `globset` compiles many globs into one automaton, the natural next step for "match this path against 5000 ignore rules".
- **Pike VM vs DFA.** The simulation you wrote is a *Pike VM* (thread list per position). Converting it into a **DFA** on the fly (cache the set of states you reached) gives one table lookup per character, which is how `grep` and RE2 reach gigabytes per second; the cost is that the number of DFA states can be exponential, so real engines cap the cache and fall back. For globs, which are much simpler than regular expressions, a DFA is usually small.
- **Bitsets for small programs.** If the program has at most 64 states, the state set fits in a `std::uint64_t`; epsilon closure and the step become a handful of bit operations and nothing allocates. A `std::bitset<N>` or a small-vector in the object gives the same for bigger sizes. The version here allocates four vectors per call; the tests only demand that the number does not grow with the path.
- **Bytes vs characters.** `?` here matches one byte. A UTF-8-aware matcher decodes code points (`?` should match `é`, which is two bytes) and handles case folding with Unicode tables (ICU, `std::towlower` with a locale, or `utf8proc`); file systems differ again (macOS normalises names to NFD, Windows is case-insensitive but case-preserving, Linux is bytes). `ignore_case` here is ASCII-only on purpose.
- **Security.** Pattern matching of attacker-controlled input is a classic ReDoS (regular expression denial of service) surface. Having a *provable* `O(n * m)` bound, a limit on nesting depth, and no recursion on input size is what makes a matcher safe to expose; the tests with a million-character pattern are the regression test for that promise. Also remember that matching is not path *sanitising*: `../` and symlinks need `std::filesystem::weakly_canonical` and checks against the root.
- **gitignore subtleties** that this lesson leaves out on purpose: patterns without a `/` match at any depth, a trailing `/` means "directories only", `!pattern` re-includes, a later rule overrides an earlier one, and a directory excluded by a rule hides everything below it even if a later negation names a file inside it.
