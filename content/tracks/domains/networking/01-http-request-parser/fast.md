# Fast path: what's different in C++

- **`std::string_view` is what makes incremental parsing cheap.** `data.substr(used)` is a pointer and a length; slicing the input into the pieces the parser consumes costs nothing and never copies. In Java or Python the same code would allocate a substring per step.
- **No hidden quadratic behaviour.** `std::string::append` is amortised O(1), but `body = body + chunk` rebuilds the string every time (O(n) per call, O(n²) overall), and `buffer.find("\r\n")` over the whole buffer re-reads old data. The tests deliver 1 MB one byte at a time precisely because that is what a slow or malicious client does.
- **Parsing numbers.** `std::stoul` skips whitespace and accepts a sign and trailing text; `std::from_chars` (C++17) is stricter (no whitespace, no `+`, no prefix, reports overflow) but still accepts a leading `-` for signed types and stops at the first non-digit without complaining, so you must check that it consumed the whole field. For `Content-Length` a ten-line digit loop with an explicit overflow check is clearer and safe by construction.
- **Production parsers.** `llhttp` (Node.js), `picohttpparser`, `nghttp2`/`nghttp3`, Boost.Beast and Envoy's HTTP codec are all state machines of this kind; `llhttp` is generated from a description of the state graph. Most of their security fixes over the years are exactly the rules in the table: ambiguous framing, line endings, and overflow.
- **Request smuggling is a protocol-level bug, not a memory bug.** Rust or Go parsers can be vulnerable too. What C++ adds is that a *lenient memory* bug on top (reading past a buffer after a wrong length) turns a desynchronisation into a data leak; hence the explicit limits and the span/view-based interface.
