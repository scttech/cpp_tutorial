# Fast path: what's different in C++

- **Real build systems.** **ninja** is the model for this lesson: it reads a graph and rebuilds only what is out of date, in parallel; **CMake** generates ninja/make files; **Bazel**/**Buck2**/**Pants** hash *contents* instead of trusting timestamps (so touching a file without changing it rebuilds nothing, and results can be cached across machines); **ccache**/**sccache** cache compiler invocations. Timestamps (`make`) are cheap but fragile (clock skew, `git checkout` resetting times); content hashes are robust but need hashing every input.
- **`std::filesystem` for the timestamps.** `std::filesystem::last_write_time(path)` returns a `file_time_type`; `exists(path)` tells you about missing outputs. The plan function here takes an `unordered_map` so that it is pure and testable; a real tool fills it with `last_write_time`, one `stat` per file, which is the bottleneck on big trees (ninja stores a build log to avoid most of them).
- **Dynamic dependencies.** Real compilers discover dependencies while compiling (`-MMD` writes the headers an object file really includes). Ninja loads these "depfiles" after the first build, so the graph grows between runs; a header added to a `#include` is a new edge. The graph class here is immutable, which is a good first approximation and a bad last one.
- **Cycle reporting and graph libraries.** **Boost.Graph** (`topological_sort`, `strong_components`, `depth_first_search` with visitors) is the heavyweight option; its DFS also uses colour maps and reports back edges through a visitor, which is how you would extract the cycle. A *strongly connected component* decomposition (Tarjan, Kosaraju) finds **all** cycles at once, which is what a good linker error for static initialisation order or an IDE's "cyclic include" view wants. The standard library has none of it.
- **Deterministic builds.** The tie-break by declaration order is the same idea as reproducible builds: the same inputs must give the same order and (ideally) the same bytes, regardless of `unordered_map` iteration order, filesystem listing order or thread scheduling. `std::unordered_map` iteration order is *unspecified*, which is why this implementation only uses it for look-ups.
- **Scheduling.** `levels` is a simple greedy layering. A real scheduler is a work queue: when a target finishes, decrement its dependents' counters (exactly Kahn's algorithm, but with workers instead of a loop) and start whatever reaches zero, preferring targets on the longest remaining path (the *critical path* heuristic) to keep all cores busy.
