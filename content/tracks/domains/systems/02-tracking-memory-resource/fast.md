# Fast path: what's different in C++

- **Allocators as part of the type, or not.** `std::vector<T, A>` bakes the allocator into the *type*; two vectors with different allocators are different types. `std::pmr::vector<T>` fixes the allocator type to `polymorphic_allocator` and makes the *resource* a runtime value, so you can swap a tracking, arena or pool resource without changing any signatures. This is C++17's answer to the long-standing allocator pain; Rust has the `allocator_api` (unstable), Java and Go have no per-container allocators.
- **Hooking `operator new` vs a resource.** Replacing global `operator new` (the other classic way to count allocations, and what the test framework itself does) is all-or-nothing and process-wide. A `memory_resource` is *scoped*: only containers constructed with it are tracked, which is what you want for "this subsystem leaked".
- **Leak checkers you already have.** AddressSanitizer's LeakSanitizer (`-fsanitize=address`) and Valgrind report leaks at exit with call stacks. A tracker like this gives you *live* numbers (current, peak, per-subsystem) in a running process, at a cost of a hash-map operation per allocation, so it is usually compiled in only for debug and test builds, or sampled.
- **Why `do_is_equal` is identity.** Two resources are equal when memory from one can be freed through the other. Two trackers each have their own books, so they are not interchangeable even with the same upstream. Containers use this to decide whether a move can steal memory or must copy it.
- **Real-world cousins.** `tcmalloc`/`jemalloc` profiling, Chromium's `base::allocator`, Unreal's `FMalloc` wrappers, and Google's `absl::` and Bloomberg's `bsl::` allocator-aware libraries all work this way.
