# Fast path: what's different in C++

- **`constexpr` runs your code in the compiler.** A C table generator would be a script that prints a 256-line array, or a function called at start-up (and a race if two threads call it). In C++ the *same C++ function* produces the table during compilation, and `static_assert(Crc32::compute("123456789") == 0xCBF43926)` makes the compiler **test your CRC while building**. Rust has `const fn`, Zig has `comptime`; Python and Java have no equivalent.
- **Non-type template parameters of class type (C++20).** `template <class T, CrcParams<T> P>` lets a whole struct be a template argument, so `Crc<uint32_t, kCrc32>` and `Crc<uint32_t, kCrc32C>` are different types with different compile-time tables. Before C++20 you needed a long list of `template <uint32_t Poly, uint32_t Init, bool RefIn, ...>`.
- **`std::span<const std::uint8_t>`** takes a vector, an array, a C buffer and a length, or a sub-range, without copying; the `std::string_view` overload covers text. Embedded APIs that take `(const uint8_t* p, size_t n)` pairs get both from one parameter.
- **Hardware CRC instructions.** x86 has `crc32` (SSE 4.2, the Castagnoli polynomial, = CRC-32C), ARMv8 has `crc32b/h/w/x`, many microcontrollers have a CRC peripheral. Production code chooses at build time: peripheral where present, **slice-by-8** tables (8 tables, 8 bytes per step, about 4 times faster than the byte-wise table) otherwise, and the byte-wise table you wrote here for small parts with little flash.
- **What CRCs are *not*.** They detect accidental corruption (all single-bit errors, all bursts up to the width) but are trivially forgeable; they are not hashes and not authentication. Use HMAC or an AEAD for security.
