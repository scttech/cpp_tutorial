# Fast path: what's different in C++

- **A data race is undefined behavior**, not just a wrong result: two threads touch the same non-atomic location, one writes, no happens-before relation between them. Races are about *memory*, not about time. Detect with `-fsanitize=thread` (5-15x slower, finds races that did not misbehave this run).
- **`std::mutex`** + RAII locks: `std::lock_guard` (simple), `std::unique_lock` (movable, unlockable, needed for condition variables), `std::scoped_lock` (C++17, several mutexes, deadlock-free), `std::shared_mutex` + `std::shared_lock` (readers/writer). Never `lock()`/`unlock()` by hand. `std::recursive_mutex` exists and usually signals a design problem.
- **Rules**: every access to shared mutable data (reads too) holds the same mutex; the mutex lives with the data (`mutable` for const accessors); critical sections are short; no callbacks or I/O under a lock; check-then-act under one lock.
- **Deadlock**: circular waiting. Prevent with a global lock order, `std::scoped_lock`/`std::lock` for several mutexes, no lock held while waiting for another thread, `try_lock` with back-off. TSan reports potential deadlocks as lock-order inversions. A consistent snapshot of several locked objects = lock all in the same order.
- **One-time init**: `std::call_once`/`std::once_flag`, or a function-local static (thread-safe since C++11). **Per-thread data**: `thread_local`. **Immutable data** shared between threads needs no lock (after it was published safely: before the threads start, or through `join`/a mutex).
- **Contention**: a mutex held for long, by many threads, serializes the program. Measure before reaching for lock-free tricks. False sharing (two threads writing different variables in one cache line) also costs; pad with `alignas(std::hardware_destructive_interference_size)`.
