# Fast path: what's different in C++

- **No parser in the standard library.** C++ hands you `int main(int argc, char** argv)` and nothing else. In practice: **CLI11** (header-only, the most popular modern one: subcommands, validators, config files, help generation), **cxxopts**, **argparse** (a C++ port of Python's), **Boost.Program_options** (powerful, heavy), **lyra**, **clipp**, **popl**; or POSIX `getopt`/`getopt_long` (C, global state, not thread-safe, no help text). Python's `argparse`, Rust's `clap` and Go's `flag`/`cobra` set the expectations.
- **`std::string_view` for arguments.** `argv` strings live for the whole program, so views of them are safe and free. The tests pass `string_view`s; the parser copies only what it stores (values and positionals) into `std::string`, because a `Parsed` result may outlive the argument array of a test or a REPL line.
- **`std::span` for the argument list.** `std::span<const std::string_view>` accepts a `std::vector`, an array, or `{argv + 1, argc - 1}` converted once; the parser does not care where the arguments come from, which is what makes it testable without a process.
- **`std::from_chars` / `std::to_chars` (C++17, `<charconv>`).** The floating-point overloads need a recent library (GCC 11, Clang with libc++ 20, MSVC 2019 16.4); they are locale-independent and correctly rounded, unlike `strtod` which obeys `setlocale` (a famous cause of "1,5" bugs). Parse errors come back as `std::errc::invalid_argument` and `result_out_of_range` instead of exceptions.
- **Windows.** `wmain`/`wchar_t**` and a command line that is one string split by the C runtime's rules (quotes and backslashes); on Unix the shell does the splitting and globbing before you see anything. A parser operates on the already-split list; `*.cpp` expansion is not yours to do on Unix, and is your job on Windows.
- **Design lessons from the big libraries.** Subcommands (`git commit -m`), environment-variable fallbacks, config files, shell completion generation (`--generate-completion=bash`), and *did-you-mean* suggestions (edit distance, as in `git`'s "The most similar command is...") are what real tools add after this core. Exit codes: 0 success, 1 failure, 2 usage error (the sysexits.h convention is `EX_USAGE` 64).
