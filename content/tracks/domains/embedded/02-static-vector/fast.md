# Fast path: what's different in C++

- **Object lifetime is separate from storage.** In Java, Python or Go an object exists as soon as its memory does. C++ lets you reserve bytes first and begin an object's life later (`construct_at`/placement `new`) and end it earlier than the memory (`destroy_at`). `std::vector` uses exactly this to keep spare capacity without constructing anything; a static vector does the same without a heap.
- **`std::inplace_vector<T, N>` is C++26's standard version of this exercise**, and `boost::container::static_vector`, ETL's `etl::vector` and `folly::small_vector` are the established libraries. Embedded C++ projects use them (or their own) because exceptions, `new` and `malloc` are often forbidden by the coding standard (MISRA, AUTOSAR, JSF).
- **No exceptions means a different API.** `std::vector::push_back` throws `bad_alloc` when memory runs out; here "full" is a normal, expected outcome, so `push_back` returns `bool` and `emplace_back` returns a pointer or `nullptr`. Rust's `heapless::Vec::push` returns `Result<(), T>` for the same reason.
- **`std::launder` and strict aliasing.** Casting `std::byte*` to `T*` is only legal if a `T` really lives there; `launder` is the compiler-visible "yes it does" for objects created by placement new. C code just casts and hopes.
- **Move assignment into a dead slot is a bug.** Assigning (`=`) calls the *assignment operator*, which assumes `*this` is already a valid object. For a slot whose object was never constructed (or already destroyed) you must *construct*. Mixing the two up is the classic bug in hand-made containers, and it is why the tests count constructions, destructions and moves separately.
