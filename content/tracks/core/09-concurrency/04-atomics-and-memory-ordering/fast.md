# Fast path: what's different in C++

- **`std::atomic<T>`** (`<atomic>`): indivisible `load`, `store`, `exchange`, `fetch_add/sub/and/or/xor`, `compare_exchange_weak/strong`; `is_lock_free()`; `std::atomic_flag` (`test_and_set`, `clear`, `test`); `std::atomic_ref<T>` (C++20) for non-atomic objects. `volatile` is NOT atomic and gives no ordering between threads (it is for memory-mapped hardware). Non-atomic shared data that is written is a data race even if "it is just an int".
- **A sequence of atomic operations is not atomic**: use a compare-exchange loop (`while (!a.compare_exchange_weak(old, f(old))) {}`; the failed exchange refreshes `old`) or a mutex.
- **Memory orders**: `relaxed` (atomicity only: counters), `acquire` (loads) / `release` (stores) / `acq_rel` (read-modify-write): a release store that is observed by an acquire load makes all writes before the store visible after the load (publication, locks); `seq_cst` (default) adds one total order. `consume` is deprecated in practice. Start with the default; weaker orders are an optimization with proofs obligations. TSan models them, so it finds missing acquire/release.
- **Spin locks**: `while (flag.test_and_set(acquire)) pause/yield; ... flag.clear(release)`. Fine for a few instructions on dedicated cores, terrible when the holder can be descheduled (always yield/sleep eventually) or on one core. A `std::mutex` is usually better.
- **Waiting**: `std::atomic<T>::wait(old)` / `notify_one` / `notify_all` (C++20) sleep until the value changes: use these instead of polling. `std::atomic<std::shared_ptr<T>>` (C++20) exists.
- **Lock-free is hard**: ABA, memory reclamation (hazard pointers, epochs, RCU; `std::hazard_pointer`/`std::rcu` are C++26), progress guarantees (wait-free / lock-free / obstruction-free), false sharing (`alignas(std::hardware_destructive_interference_size)`). Use a tested library (Boost.Lockfree, folly, moodycamel, Concurrency Kit) or a mutex.
- **Fences** (`std::atomic_thread_fence`) order non-atomic and relaxed accesses without a particular variable: rarely needed.
