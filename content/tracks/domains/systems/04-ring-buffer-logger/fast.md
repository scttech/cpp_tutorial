# Fast path: what's different in C++

- **No allocation on the hot path is a design property, not an optimisation.** Languages with garbage collectors (Java, Go, C#) log by creating objects, and their loggers fight GC pauses; Python's `logging` builds a `LogRecord` per call. A C++ logger can be written so that `log()` only does `memcpy`-like work into memory reserved at construction, which is why game engines, trading systems and kernels (Linux `printk` ring buffer, `dmesg`) are built this way. The test framework here counts `operator new` calls to prove it.
- **`std::string_view` as the message parameter** accepts string literals, `std::string`s and slices without constructing anything. The old interface `const std::string&` would allocate a temporary for every `log("literal")` call.
- **Serialising by shifts instead of `memcpy` of a struct.** Writing `struct Header { uint8_t level; uint64_t seq; uint32_t len; }` straight into the buffer would leave padding bytes, depend on the machine's endianness, and need aligned access. Shifting out bytes gives a *defined*, portable, compact format, the same technique network protocols and file formats use.
- **Ring buffers everywhere.** The same circle with `head`/`tail` indices is the `std::queue` of the kernel (`kfifo`), of audio pipelines, of the lock-free SPSC queue in this track's Finance challenge, and of `boost::circular_buffer`. The variable-length-record version here is what `dmesg`, journald's in-memory buffers and Android's `logd` do. Note that C++ has no standard ring buffer: `std::deque` is not one, and it allocates.
- **Thread safety** is left out on purpose. A shared recorder usually gets one ring *per thread* (so no lock is needed at all) and a merge by sequence number or timestamp when dumping.
