# Fast path: what's different in C++

- **Node containers promise stable addresses.** `std::list` and `std::unordered_map` never move their elements when other elements come and go (`std::vector` does). Interview-style "LRU in Python" uses `OrderedDict` or `functools.lru_cache`; Java has `LinkedHashMap` with `accessOrder`. C++ has no ready-made one in the standard library, so you build it from `std::list` + `std::unordered_map` and the stability guarantees are what make it correct.
- **`splice` is the move-without-moving operation.** It exists only for the node-based containers (`list`, `forward_list`) and also works *between* two lists. Python's `deque` and Java's `LinkedList` have no such operation.
- **Hashing is pluggable.** The `Hash` template parameter lets the tests count calls; in production it is where you plug in a better hash (`absl::flat_hash_map`, `boost::unordered_flat_map`) for 2 to 5 times the speed. Memory locality is the weakness of this classic design: every node is its own allocation, so real caches (Caffeine, ristretto, Linux page cache) store entries in arrays with indexes instead of pointers.
- **Thread safety is a separate decision.** This cache is not thread safe, and `get` writes (it reorders the list), so even readers need an exclusive lock. High-throughput caches shard by key hash, one lock per shard, or record accesses in a buffer and apply them in batches.
- **LRU is not the only policy.** It is vulnerable to scans (one pass over a huge file evicts everything useful). Production systems use LRU-K, 2Q, ARC, CLOCK or TinyLFU for this reason.
