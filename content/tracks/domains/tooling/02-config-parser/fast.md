# Fast path: what's different in C++

- **Use a library in production.** **toml++** (header-only, complete TOML 1.0, excellent error positions), **tomlplusplus**, **inih** (INI), **yaml-cpp**, **nlohmann/json** and **simdjson** (JSON), **Boost.PropertyTree**, and for hierarchical configs with includes **libconfig** or **HOCON**. Rust's `serde` + `toml` and Python's `tomllib` (3.11) are the models. This lesson is the cheapest way to see what they do for you.
- **`std::from_chars` for the conversion.** It is locale-independent (unlike `strtod`, which obeys `setlocale` and turns `"1.5"` into 1 in a German locale), allocation-free, and reports `result_out_of_range` instead of returning `HUGE_VAL` with a global `errno`. The grammar checks stay yours because `from_chars` accepts things config files should not (`"inf"`, `"nan"`, `"1."`, hexadecimal floats with a flag).
- **`std::string_view` as the cursor.** The parser never copies the input: it slices it. Only the *results* (keys, string values) are copied into `std::string`. A faster parser would return views into the input for strings without escapes, at the cost of tying the config's lifetime to the text buffer; that is exactly what `simdjson` does (and what its "on-demand" API warns you about).
- **Errors as values.** Exceptions would make the happy path as fast but the code harder to read and the library unusable in `-fno-exceptions` builds (games, embedded, browsers); `std::expected<Config, Error>` (C++23) is the standard spelling of the `{config, error}` pair used here, with monadic helpers (`and_then`, `transform_error`).
- **Column units.** Bytes (here), UTF-16 code units (what LSP/VS Code use for editor positions) or Unicode code points/grapheme clusters (what humans count) are three different answers for the same position, so a language server converts. The caret rendering with tabs preserved is the cheap trick that makes bytes look right in a terminal.
- **Security.** Config parsers are attack surface: depth limits against stack exhaustion (the test nests 500 arrays; a real parser caps the depth), size limits, rejecting duplicate keys (a classic smuggling vector in JSON: parsers disagree about which `"role"` wins), and never evaluating anything. Recursive descent on untrusted input needs an explicit nesting limit or an iterative parser.
