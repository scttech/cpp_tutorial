# Fast path: what's different in C++

- **Prefer a member over a base class** unless you need substitutability or must override a virtual function. A member can be a plain object (no heap, no indirection): `IntBag bag_;`. Private inheritance (lesson 1) is the unusual middle road: "implemented in terms of" with the option to override.
- **The fragile base class problem**: a base class that calls its own virtual functions (a "self-use" of the interface) makes every override a dependency on that detail. Documented self-use is part of the contract (see the Template Method pattern); undocumented self-use is a trap. The advice of *Effective Java* Item 19 ("design and document for inheritance, or else prohibit it") applies in C++ too: mark classes `final` when they are not designed for it.
- **Strategy pattern**: hold the varying behavior as a member behind an interface (`std::unique_ptr<Movement>`), swap it with a setter. The C++ alternatives that avoid the virtual call are templates (a policy type parameter) and `std::function`, lesson 5.
- **Owning polymorphic parts**: `std::unique_ptr<Interface>` members make a class **move-only** (the copy constructor is implicitly deleted). For copies, give the interface a virtual `clone()`; for value semantics, type erasure (lesson 5).
- **Open/closed**: a new part needs only a new class that implements the interface; the owner is untouched.
- **Diamond**: with ordinary multiple inheritance, a base reached by two paths exists twice. `virtual` inheritance shares it. The **most derived class initializes the virtual base**, directly in its member-initializer list; virtual bases are constructed first, and destroyed last. Costs: extra indirection to reach the base's members, a larger object, and no `static_cast` down from a virtual base.
- **Interface inheritance is safe to multiply; implementation inheritance is not.** Java and C# forbid multiple inheritance of classes for this reason (interfaces only); C++ allows both and leaves the discipline to you.
