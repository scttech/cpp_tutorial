# Fast path: what's different in C++

- **Reading integers from bytes: shifts, not casts.** `*reinterpret_cast<const uint32_t*>(p)` is undefined behaviour twice over: the pointer may be misaligned (a crash on some CPUs) and it violates strict aliasing (the optimizer may reorder or delete the read). `memcpy` into a local is legal and compilers turn it into one load; shifts like `(p[0] << 24) | (p[1] << 16) | ...` are portable and also compile to a single `mov` + `bswap` on x86. Java's `ByteBuffer.order()`, Python's `struct.unpack('>I', ...)` and Go's `binary.BigEndian.Uint32` do the same job; C++26/`<bit>` adds `std::byteswap`/`std::endian`.
- **`std::span` and `std::optional` replace the C idiom of `(uint8_t* p, size_t n)` plus an error code.** `optional` makes "this read can fail" part of the type so a missing check does not compile into silent garbage; `span` carries the length so `subspan` can be checked. Both are zero-overhead.
- **Promotion again.** `uint8_t << 24` is computed in `int`, which overflows into the sign bit for values above 127: always widen first (`static_cast<uint32_t>(b) << 24`). The same trap hits `b << 56` on a `uint8_t` (undefined behaviour for shifts of a promoted value by 32 or more, so use `uint64_t`).
- **Varint and zigzag in the wild.** Protobuf (all integers), FlatBuffers offsets, WebAssembly (LEB128), SQLite's varint, Git packfiles, DWARF, Apache Avro and Thrift's compact protocol. The strictness rules (canonical form, 10 bytes, overflow bit) are what well-fuzzed decoders such as Google's `protobuf::io::CodedInputStream` enforce.
- **Checksums are not security.** XOR-and-seed here teaches the framing; in a real protocol use CRC-32 for accidental corruption (see the Embedded track) and an authenticated cipher (AES-GCM, ChaCha20-Poly1305) when an attacker is in the picture.
