# Fast path: what's different in C++

- **No CSV in the standard library.** C++ streams give you `std::getline(in, line, ',')`, which is exactly the "split on commas" parser that breaks on quoted fields. In practice you use a library: **Boost.Spirit**-based parsers, **fast-cpp-csv-parser**, **Apache Arrow's CSV reader** (multi-threaded, type-inferring), **rapidcsv**, or **DuckDB's CSV sniffer**, which also guesses the dialect. Python's `csv` module and `pandas.read_csv` are the models for the API.
- **`std::string_view` for zero-copy fields.** A fast reader returns `string_view`s into the input buffer and only allocates for fields that contain `""` (which need unescaping). The reuse-the-vector design here gets most of the benefit with a simpler interface; the cost of returning views is that they die with the buffer.
- **`std::from_chars` for the numbers.** After you have the field, `std::from_chars(first, last, double&)` (C++17) parses without locale, allocation or exceptions and is several times faster than `stod` or `istringstream`. Locale-dependent parsing is a classic data bug: `1,5` is 1.5 in German, and `std::stod` honours the global locale.
- **mmap and chunking.** Large files are memory-mapped and split at newline boundaries for parallel parsing; the catch (and a reason RFC 4180 is hard to parallelise) is that you cannot tell whether a newline is inside quotes without scanning from the start. Real engines use speculative parsing and re-check.
- **CSV injection.** A field that begins with `=`, `+`, `-` or `@` is executed as a *formula* when the file is opened in Excel (`=HYPERLINK(...)`, DDE). If you export user-supplied data, escape such fields (usually by prefixing a single quote) as a separate, documented step: it intentionally breaks the round trip.
- **The BOM is not a joke.** Excel on Windows wants a BOM to recognise UTF-8; other tools choke on it. Decide on purpose, on both the read and the write side.
