# Fast path: what's different in C++

- **Small integers on purpose.** `std::uint16_t` counters keep the object to a few bytes and make wrap-around a *design question* you must answer (saturate). In Python or JavaScript integers never overflow; in Java they silently wrap; in C++ unsigned arithmetic wraps by definition and signed overflow is undefined, which is why firmware code states its widths (`<cstdint>`) and chooses saturation or wrapping explicitly.
- **Integer promotion traps.** `uint8_t | uint8_t` is an `int`; `events |= kPressed` works because compound assignment converts back, but `events = events | kPressed` needs a cast. Unscoped `enum Event : std::uint8_t` is used here (not `enum class`) exactly so that bit flags combine without a pile of operator overloads; for stricter code, define `operator|` on an `enum class` or use `std::bitset`/`std::byte` with `std::to_integer`.
- **`update()` as a function you can call from an ISR.** No allocation, no exceptions, no blocking, no virtual calls and no `std::function`: the same constraints as the other embedded challenges. Classes like this are also trivially unit-testable on a PC, which is the main reason to write firmware logic as plain C++ with the hardware access pushed to the edges.
- **Debouncing alternatives.** Shift-register debouncing (`history = (history << 1) | raw; stable if history == 0x00 or 0xFF`) is branch-free; integrator debouncing (count up while high, down while low, with limits) tolerates noisy lines; a hardware RC filter plus a Schmitt trigger removes bounce before the code ever sees it. Counting consecutive samples is the simplest to reason about and test.
