# Fast path: what's different in C++

- **Pass the clock in.** C++ makes it tempting to call `std::chrono::steady_clock::now()` inside the limiter; resist it. A limiter that takes `now` as an argument is deterministic, trivially testable (the tests here simulate 100000 ticks in microseconds), and lets one caller read the clock once per batch. Java's `Guava RateLimiter` and Go's `golang.org/x/time/rate` expose the same split (`AllowN(t, n)`).
- **Unsigned arithmetic wraps; signed overflow is undefined.** `uint64_t` subtraction `now - last` with `now < last` silently produces ~1.8e19, and multiplication wraps modulo 2^64. Both are well-defined but wrong for this problem, which is why the code compares before it subtracts or multiplies. (With `int64_t` the same overflows would be *undefined behaviour*: the compiler could delete your check.) GCC/Clang provide `__builtin_mul_overflow`; C++26 has `std::mul_sat`.
- **`std::deque` vs `std::vector` vs a ring buffer.** The window is a FIFO: push at the back, pop at the front. `deque` does both in amortised O(1), at the price of chunked memory. A fixed-size ring buffer of `limit` timestamps (the Embedded track's logger shows the idea) uses one allocation and is faster, but needs `limit` known up front. Redis' `CL.THROTTLE` and Envoy's local rate limit use token buckets; Cloudflare and Stripe describe sliding windows with counters (a two-bucket approximation) to avoid storing every timestamp.
- **Distributed limits** need shared state (Redis, a gossip protocol) and accept approximation; the single-node exactness here is the building block they approximate.
- **`unordered_map::erase(iterator)` returns the next iterator**: the idiom `it = map.erase(it)` inside a loop is how to delete while iterating without invalidating the loop (erasing with `map.erase(key)` inside a range-for is undefined behaviour).
