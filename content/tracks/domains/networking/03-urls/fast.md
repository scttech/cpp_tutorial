# Fast path: what's different in C++

- **No standard URL class.** C++ has `std::filesystem::path` for files but nothing for URLs. Libraries: Boost.URL (the C++ standards-track one), `ada` (the WHATWG-conformant parser that Node.js uses, with SIMD), `uriparser`, Poco::URI, Qt's `QUrl`. Python has `urllib.parse`, Java `java.net.URI`, Go `net/url`, JavaScript the `URL` class; each differs slightly from the RFC in edge cases (the WHATWG URL standard that browsers implement is *not* identical to RFC 3986), which is the root of many parsing-differential security bugs.
- **`std::string_view` makes the parser allocation-free in principle.** A production parser stores views into the original text and never copies; this exercise returns `std::string`s for simplicity, and the "fast" tier checks the inner functions (dot-segment removal, percent coding) run in linear time with at most one allocation for the result.
- **`std::optional<std::string>` for "present but empty".** A `std::string` alone cannot tell `http://a/p` from `http://a/p?`; `optional` can. The same pattern works for any "absent versus empty" field (JSON `null` versus `""`).
- **Never build text by erasing from the front.** `s.erase(0, n)` shifts the whole remaining string: a loop of those is O(n²). A `string_view` with `remove_prefix(n)` is O(1). The dot-segment test with 600000 segments exists to punish the first version.
- **Normalisation is for comparison, not for security.** Two URLs that normalise to the same string are *probably* the same resource, but only the server decides what a path means; never use string prefix checks on a URL path to make an access-control decision without decoding and normalising it exactly as the server will.
