# Fast path: what's different in C++

- **`std::string_view` is the right parameter for read-only text.** It takes a `std::string`, a literal or a substring without copying, and a tokenizer that only *reads* has no reason to own the input. The price: a view does not own anything and does not guarantee a terminating `\0`, so `line[i + 1]` past the end is an out-of-bounds read, which is exactly what the "poison after the view" test hunts. Python's `str` slicing and Java's `substring` copy; Go's string slices and Rust's `&str` are views like this one.
- **Hand-written lexers vs generators.** `lex`/`flex`, `re2c` and Rust's `logos` generate state machines from rules; for a language this small a `while` loop with one branch per character class is faster to write, to step through in a debugger, and to give good error positions. `std::regex` is the wrong tool: it is slow, can overflow the stack on long inputs, and cannot express "quotes join neighbours" cleanly.
- **Real shells are harder than this.** POSIX also has `$(...)`, backticks, `$((...))`, `~`, globbing, here-documents, `2>&1`, line continuation, and word splitting of expansions (which is how `rm $FILE` with spaces in `FILE` becomes a famous bug). Libraries such as Python's `shlex.split` and Rust's `shell-words` implement subsets exactly like this exercise.
- **Report positions, not just failures.** Parsers that return only "error" are painful to use; carrying a byte offset (or a line/column) through a `Result` struct is what makes compiler-quality diagnostics possible. C++23 adds `std::expected<T, E>` for this shape; here a plain struct does the job.
- **Security note.** Tokenizing is where injection bugs live. If you ever pass user text to a real shell (`system()`, `popen()`), you need exactly this logic to quote it correctly; prefer `execve`-style APIs that take an argument vector and never involve a shell.
